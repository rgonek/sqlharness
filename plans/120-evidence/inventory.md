### Explicit unsupported combinations and scope boundaries

- A CLI `compare` with named parameter-set files is unsupported. Do not emit `--param-set` for compare, convert the sets into separate compare operations while claiming identical case/session/evidence semantics, or call CLI matrix and MCP named-set inputs interchangeable.
- CLI compare's one-parameter text matrix cannot express an empty string or typed NULL value. MCP's structured matrix can express both distinctly. Ticket A therefore documents a shape available through MCP named set files but not as one equivalent CLI compare request. No claim of CLI/MCP parity is made.
- MCP does not accept fixed-parameter files; its supported set-file shape is a named set file. CLI fixed `--params-json` is a different shape from MCP `parameterSetFiles`.
- A manifest-relative path is not automatically a valid MCP file path: MCP requires an absolute path under its startup-frozen input roots. A future resolver must resolve relative references without weakening those roots or allowing symlink/reparse escapes. If this cannot be guaranteed, reject that manifest candidate.
- The candidate 16-entry suite cap and 1 MiB manifest cap are study decisions. Existing 1–32 parameter-set and matrix bounds remain authoritative; the study caps must not be described as product limits.
- Hash verification protects file-byte identity only. It does not authorize execution, approve mutations, prove target permissions, pin a database snapshot, or validate/reuse earlier artifacts. Only explicit comparisons are modeled; no mutation, cache clear, concurrency, retry, target substitution, SQL rewriting, case inference or cross-artifact reuse is included.

## Synthetic fixtures

`fixtures/ticket-a/experiment-suite.json` has two SQL subjects and three scalar case files: small (`7`), large (`700000000`) and empty text (`""`). It intentionally uses the MCP named-set-file shape. `fixtures/ticket-b/experiment-suite.json` has three revision pairs, explicit setup, the boundary date `2024-02-29` as a fixed typed scalar, multiset comparison, and mock duplicate-sensitive rows. Its third candidate reference pins the old exact bytes while the file on disk is deliberately changed; the expected simulator behavior is to reject that entry before dispatch and stop. The original boundary-date `.sqljson` remains generated as a synthetic file-input example, while the dispatch fixture uses the CLI-supported fixed typed parameter shape. `fixtures/SHA256SUMS.txt` records exact current hashes; `ticket-b/pinned-revision.json` records both the pinned and changed digests. The generator is `fixtures/generate.ps1` and writes UTF-8 without BOM with stable LF line endings.

## Reconstruction-step count (synthetic ergonomics estimate)

These are transparent counts of input placements in the artificial Ticket A scenario, not measured user time, observed demand, model-token usage, or a claim that both surfaces have equivalent semantics.

| Representation | Counting rule | Synthetic placements |
|---|---|---:|
| Plain CLI command list expanded to one compare per subject and scalar case | 2 subjects × 3 cases = 6 commands; each command repeats target, subject, scope, baseline, candidate, case parameter, repeat, timeout, result policy and nullability policy | 60 |
| Proposed manifest | 2 entries × 10 explicit target/subject/scope/SQL/policy fields + 2 entries × 3 exact case-file references | 26 |

The 60-placement CLI expansion is only a manual reconstruction estimate: empty text is not representable in the CLI matrix text grammar, so that case would use fixed parameters in a separate invocation. That command list does not preserve the single named-set operation semantics shown in the MCP fixture. The proposed manifest reduces repeated literals in this counting model and adds byte pins, but the fixture does not establish recurring user demand or justify a supported runner by itself. The plain command list remains a credible alternative where operators already keep exact command lines; “no new feature” remains credible until demand is observed.
