# Plan 118 Task 2: condition difference explanation study

## Decision boundary

This is a synthetic, offline study of an optional future dashboard explanation. It does not change the product contract, journal capture, fingerprints, grouping, authorization, or comparison policy. The evaluator consumes two retained-condition records plus an existing comparison basis. It returns explanation material only and copies the supplied basis byte-for-byte at the JSON value level; it never derives or replaces that verdict.

The candidate payload is `conditionExplanation: { availability, differences, gaps, omittedDifferences }`. `availability` is `complete`, `partial`, or `unavailable`. A difference has `field`, optional exact retained `caseIdentity` and `parameterIdentity`, `kind` (`changed|added|removed`), `relation` (`measurement-condition|informational`), and optional `before` / `after` display values. A gap has only a stable `code`. `omittedDifferences` is an integer when known, including zero. Candidate bounds are 32 difference items, 16 gap items, and 8,192 UTF-8 bytes for the complete explanation JSON. These are study limits, not runtime policy.

## Evidence and comparison rules

- Compare only fields represented in both retained records. A present JSON null, typed SQL NULL, absent property, explicit `unknown`, explicit `omitted`, and empty collection are distinct states. Missing retained-value properties or parameter/case collections produce a gap; they are never treated as empty or equal.
- Explain setup SQL only when both sides retain its text; a setup-hash change alone is opaque. For parameters, compare retained effective type, list/TVP kind and shape metadata, and value only if both values are retained.
- Emit display values only when the source record marks the value `retained` and the value is present. The display layer does not interpret labels, SQL hashes, journal-keyed hashes, or whole-operation fingerprints as parameter/setup values.
- Compare parameter records only by exact parameter identity inside a uniquely paired case. Pair cases only when the fixture supplies one verified, unambiguous common measurement key. Do not pair by array position, label, ordinal, or renamed set name. Duplicate or absent keys create `case-pairing-ambiguous` or `identity-unresolved` gaps.
- A measurement-fingerprint mismatch is not itself a field difference. If no known measurement-condition difference explains it, emit `conditions-unavailable`, even when informational fields differ. If journals do not share a verified fingerprint-key domain, emit `fingerprint-domain-unverified` and do not use those fingerprints to pair cases.
- Keep regular `Fingerprint` separate from `MeasurementFingerprint`. Regular fingerprints include comparison mode; measurement fingerprints omit it. Only an unexplained measurement-fingerprint mismatch requires `conditions-unavailable`; a comparison-mode-only regular-fingerprint change is informational and does not imply the measurement key changed. A mismatch accompanied only by informational differences remains unexplained and gets the gap.
- `omitted` paths yield `field-omitted`; unavailable legacy records yield `legacy-model-unsupported`. Known differences can coexist with gaps, resulting in `partial` availability.
- Repeat, timeout, comparison mode, warmup, operation kind, and compare-nullability are informational in this study. Their differences do not alter the immutable basis or become measurement incompatibilities. Regular fingerprints include comparison mode while measurement fingerprints omit it; repeat and timeout are omitted from both. The fixture's comparison-mode-only case therefore has different regular fingerprints but the same measurement fingerprint. No equality claim about untracked settings follows from a matching fingerprint.
- Difference order is deterministic by field path, exact retained case identity, parameter identity, and kind. Gaps are unique and sorted by stable code. Omission accounting counts every candidate item removed by an item or UTF-8 budget.
- The evaluator reserves a truthful `budget-exceeded` gap when truncating. It preserves item identities and reports exact omitted item count; if the serialized explanation itself cannot fit after dropping values, it retains identity/kind/relation and removes display values before dropping differences. A final irreducible overflow is represented by `availability: partial`, the budget gap, and a known omission count.

## User-facing wording

Use “Recorded measurement conditions differ” for known measurement-condition differences, “Some recorded details are unavailable” for gaps, and “These settings changed but do not determine this comparison group” for informational changes. Show actual retained values only when available. Do not expose serializer terms such as null JSON or HMAC; do not call an unavailable value “NULL” or say that a hidden parameter changed.

## Future dashboard route/component map

Current routes do not expose a safe cross-group explanation pair. `OptimizationSection` selects one conditions group and one scope, then chooses versions A and B from that scope. The session and agent-session `/optimization/compare` handlers resolve the requested fingerprint to exactly one group and pass evidence from only that group/scope to the comparer. The response has exact `beforeAction` and `afterAction` references, but both sides still come from the selected single group. It cannot select one side from each of two conditions groups. Defer a group-selector explanation for cross-group condition differences until an existing interface exposes both group identities and the exact operation pair; do not add selectors or infer identity from labels.

The operation route `/api/operations/{id}/optimization` is anchored to one compare operation. It obtains one `CompareEvidence`, then calls the comparer with `[ownEvidence]`; the resulting before/after action references describe that operation's baseline/candidate SQL variants. They do not identify a pair of operation condition records from distinct groups. Defer cross-group condition explanations on this route too unless a later interface supplies that exact pair. For a later same-operation explanation, use only the exact baseline/candidate data represented by that operation and preserve its existing basis. `ComparisonPanel` renders comparison and basis; `optimizationMarkdown.ts` owns copied Markdown wording. These locations are a map for later work, not edits in this study.

Once a safe pair across condition groups is available, the group-selector path can host the explanation near `ComparisonPanel` and `optimizationMarkdown.ts`; current group selection alone is insufficient for cross-group differences. The operation-pair path is currently anchored to one compare operation and does not supply two operation condition records, so defer cross-group explanation there as well. Do not expand either API surface during this study. Any later explanation must remain downstream of existing grouping/comparison and must not alter `basis`.

## Study output and limits

`cases.json` contains synthetic records only. `evaluate.ps1` is a standalone candidate evaluator; `verify.ps1` is a separate oracle with hard-coded expected availability, difference identities/kinds/relations, gaps, omission counts, basis preservation, value-protection assertions, and UTF-8 bounds. `results.json` records serializer, revision, output sizes, and limitations. The study does not measure dashboard transport overhead, production serializer behavior, browser rendering, or actual journal-version prevalence.
