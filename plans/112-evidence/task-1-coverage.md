# Plan 112 Task 1: Evidence demand and existing coverage

## Finding

The observation corpus contains **one non-report optimization investigation with an explicitly selected DML bottleneck**: the `DELETE ... WHERE Key IN (...)` statement family documented in [write-statement-and-index-maintenance-evidence.md](../../docs/observations/write-statement-and-index-maintenance-evidence.md). The observed selected-bottleneck count is therefore **1 of 1 documented qualifying investigation**. This is a sample size of one, not a recurrence estimate. No frequency across installations, teams, or future investigations can be inferred.

The same note records two unmeasured hypotheses: a potentially redundant nonclustered index and list expansion into individual parameters. These are not extra bottleneck cases. The clustered key and nonclustered index are evidence of catalog shape only; neither their maintenance cost nor redundancy was measured. DML text in examples, safety tests, or other workflow observations was not counted as a selected bottleneck. Report-only case material was excluded. The corpus does not establish a broader denominator of comparable investigations or a recurrence limit beyond this single observation.

## Existing coverage and boundaries

- [Plan 063](../../plans/063-missing-index-overlap.md) captures bounded SQL Server index inventory when a saved measured plan contains missing-index hints, then compares each hint against indexes on the same table. It classifies hint coverage (`covered`, `include-gap`, `partial-key`, `new-shape`) and reports missing inventory as an evidence gap. It does not compare existing indexes against one another, measure write-maintenance cost, or recommend dropping an index. A leading-key resemblance alone is insufficient to infer redundancy.
- [Plan 083](../../plans/083-table-and-list-parameters.md) implements SQL Server TVP binding and Dapper-style list expansion for read-only query and benchmark inputs. Its contract preserves the unexpanded SQL as operation/version identity and records list length as a condition. It solves representation of the application's TVP/list input shape on those paths; it does not admit persistent DML to `query`, `measure`, or `compare`, nor provide write-cost evidence. Its recorded live SQL Server/SSMS UAT remains pending.
- [ListParameterExpander](../../src/SqlHarness.Core/ListParameterExpander.cs) expands supported list placeholders to typed parameters, and [its tests](../../tests/SqlHarness.Tests/ListParameterExpanderTests.cs) cover the supported `IN` spellings, repeated references, name collisions, empty lists, and literals/comments. This is input expansion, not canonical Query Store text normalization or proof that two statements have the same source semantics.
- The observation's numbered-parameter family can motivate a **candidate grouping heuristic**: use source/application identity where available and compare parameterized query shape while treating list cardinality as a varying condition. Require source-code and query-shape confirmation before grouping. Do not promise a canonical text normalization rule from this evidence.
