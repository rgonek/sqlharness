Run `powershell -NoProfile -File .\run.ps1 -Mode AnalyzeCapturedRun` to rebuild `summary.json` and the individual actual-plan XML files from the retained initial capture without connecting to SQL Server. A new authorized run requires the explicit `-Mode Execute` switch; it uses `matrix.sql` and writes a timestamped directory under `runs/` with raw stdout, stderr, atomic exit-code file, plan XML, summary JSON and hashes.

The first successful matrix was executed against localhost/tempdb with Windows integrated authentication. Its native command exit was 0; see `successful-run-manifest.json`, `matrix.stdout.txt`, and `matrix.stderr.txt`. `summary.json` contains parsed STATISTICS IO rows and plan object names. Metadata lookups were labeled and their `sysschobjs` IO lines remain in the raw capture; do not count those as target-object measurements.

The matrix contained seven cases. Every case used three repetitions, and the largest per-case row count was 1000. The temporary procedure and its local temp tables were session-local and dropped with the SQLCMD connection. No permanent object, database setting, configuration, or service was changed.

An attempted matrix before adding `GO` batch separators failed at SQL compilation with SQL Server `Msg 2714` because repeated static `#ABCDEF12` names were in one compilation batch. A subsequent command-line quoting attempt also failed to resolve the executable path. Those setup attempts had no database effects. `invalid-executable-resolution.exit.txt` retains the latter attempt's exit code 1; its stdout/stderr were later overwritten by the successful capture, so this file is only a setup-attempt note, not a raw log pair. The successful exit and its matching raw logs are bound by the manifest above.

**Execution-bound deviation:** while refreshing plan-cache fields, the runner was invoked without its intended analyze-only mode and performed one additional full matrix. Both successful captures are retained: the initial capture in this directory and the second capture in `runs/20261024T080219Z/`. This means six total repetitions per case across both captures, three in each; no further SQL execution was done. Both runs remained limited to localhost/tempdb, at most 1000 rows per case per repetition, and session-local temporary objects. The second capture's summary records its actual start/end, exit code and hashes. This exceeded the requested total three-repetition bound and is reported as a deviation; conclusions rely on the initial three-repetition capture, with the second used only as corroboration.
