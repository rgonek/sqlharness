## Transfer alternatives

### Server-side selected-field projection

The existing `sqlharness_query` path can carry a caller-written, statically admitted read-only catalog query and return selected scalar columns, subject to the tool's row/cell/response budgets. A purpose-built projection could select exact catalog identities and bounded scalar metadata such as plan/query IDs, engine version, compatibility level, plan hash, and compile timestamp. It avoids sending XML, and may be adequate for an identity/summary-only question.

This does not preserve an operator tree unless the query also projects XML-derived nodes. Expanding the stored XML into rows loses document hierarchy unless shape/path identity is carried explicitly; a hand-selected list can silently omit future or engine-specific evidence. It is therefore a partial view, not equivalent to the existing full-document distiller. A caller-supplied query would also require the model to compose and validate database-specific SQL. It is feasible with the existing query tool for carefully selected fields, but it is not an existing bounded catalog-plan retrieval workflow.

For SQL Server Query Store specifically, Microsoft documents `sys.query_store_plan.query_plan` as `nvarchar(max)` Showplan XML, `plan_id` as the primary key and `query_id` as the related query identity. It describes that stored plan as estimated (equivalent to `SET SHOWPLAN_XML ON`); runtime statistics reside separately in `sys.query_store_runtime_stats` and are aggregated. Thus a stored plan alone cannot be represented as current measured execution, and absent actual counters must stay unavailable rather than zero. See [sys.query_store_plan](https://learn.microsoft.com/en-us/sql/relational-databases/system-catalog-views/sys-query-store-plan-transact-sql?view=sql-server-ver17) and [How Query Store collects data](https://learn.microsoft.com/sql/relational-databases/performance/how-query-store-collects-data). The plan has not selected an engine/catalog source yet; SQL Server Query Store is a concrete comparison example, not a cross-engine retrieval design. PostgreSQL catalog selection and field equivalence remain unassessed.

### Internal complete-document distillation

The inspected `PlanDistiller` accepts full SQL Server Showplan XML offline and returns a compact JSON model: statement text, operator tree, estimates, optional runtime counters, predicates, warnings and missing-index suggestions. The 22,608-byte static fixture was accepted by the CLI `plan` route without DB access, showing that the existing distiller can handle a document larger than 4,096 characters. This is evidence about offline parse/output behavior only, not a DB retrieval path or MCP response budget.

An internal retrieval design could issue a fixed catalog read against the call's already-resolved database target, capture one selected plan privately, and pass the complete XML document directly to `PlanDistiller`. The response would contain only the existing distilled JSON model and provenance/availability fields; it must never expose raw XML or ask the model to relay the document back through `sqlharness_plan`. This retains the current projection's known fields and structural relationships without model round-trip. It still omits fields not represented by `DistilledPlan`, so “complete-document” describes parser input, not lossless output.

## Required design boundaries and current gaps

- **Target and catalog selectors:** Use the immutable per-call `McpScope` target resolved from the configured profile/request. Do not accept a database/server name or arbitrary SQL as a way to change source. For Query Store, require exact positive query/plan identifiers and verify their relationship in the selected database; cap the lookup to detect zero/ambiguous matches. The actual supported selector should be engine-specific. No such catalog selector or lookup exists in the inspected `sqlharness_plan` / `sqlharness_artifact` paths.
- **Target locking:** `McpScope` freezes the target for a call; existing database calls use per-call sessions, and independent concurrent calls are intentionally allowed (covered by MCP cancellation tests). Inspection found no cross-call target mutex in these paths. Do not invent serialization or claim an owner/target lock exists. Whether a catalog read needs additional coordination is unresolved; any future plan must preserve the current resolved target, artifact ownership checks, and session lifecycle rather than locking by caller-supplied names.
- **Read-only and provenance:** The retrieval SQL must be fixed internally and read-only; no stored-plan execution, plan forcing, arbitrary SQL, or file export. Return catalog source, query/plan identity, compile/observation timestamps and the stored/estimated classification. If runtime aggregates are requested, label their time window and aggregation separately.
- **Ingress/document caps:** Current MCP inline plan content is capped at 1 MiB UTF-8; rooted plan files at 16 MiB; file reads stop at bound + 1 byte. `PlanDistiller` caps input at 16 MiB .NET characters, 100,000 XML elements and depth 128, prohibits DTDs and disables entity resolution. A catalog-reader path must bound row count and XML size while reading/materializing as well as preserve the parser's character/element/depth checks. UTF-8 byte and .NET character ceilings are different units. Do not increase the 4,096-character output cell limit to transport source XML.
- **Cancellation:** `McpCancellationTests` passed (11/11) and establish request/process cancellation flowing through database calls and session disposal. A retrieval must pass the linked token to connection/query/read and close the session on cancellation. `PlanDistiller.Distill` is synchronous and has no token; with the existing strict parser caps, cancellation can be checked before and after parsing, but prompt cancellation during synchronous parsing is not established. A bounded parser or cancellable alternative is an implementation question, not proven by the current tests.
- **No raw XML response:** Existing `sqlharness_plan` takes exactly one caller-provided inline document or rooted file and returns a `DistilledPlan`; `sqlharness_artifact` reads saved distilled JSON. A new retrieval path must keep raw catalog XML internal and use existing result budgeting/cell clipping on the distilled response. The ordinary `sqlharness_query` path is not appropriate for returning the raw XML column because its result is model-visible and cell-clipped.
- **Existing-tool sufficiency:** Existing tools can (a) query chosen catalog scalar fields through `sqlharness_query`, or (b) distill a plan only after the caller already has its document through `sqlharness_plan`. No inspected tool joins catalog selection, bounded private document capture, attribution and distillation in one operation. A true no-round-trip retrieval therefore requires a new internal operation/tool or an equivalent extension; selected-field-only queries remain a viable narrower alternative for questions that do not need an operator tree.

## Task 2 assessment against review focus

1. **Older artifacts/missing engine fields:** Proposed retrieval should use the current distilled plan JSON shape and existing `StoredPlanReader` compatibility behavior; engine-specific fields should be explicitly unavailable. Static inspection only; no legacy artifact mutation or runtime compatibility trial was done.
2. **Identity collisions:** Require exact target-scoped query/plan selectors and preserve IDs with each response. Query Store can retain multiple plans per query; one query selector alone is insufficient to identify one plan. No live catalog enumeration occurred.
3. **Byte budgets/escaping/continuations:** The existing MCP response adapter remains responsible for result-byte and cell-character bounds. Do not send raw XML or silently change these ceilings. Internal retrieved output may need plan-node pagination if it exceeds the normal envelope; whether this is needed for real catalog plans is unmeasured.
4. **Error and negative-result meaning:** Distinguish not found, ambiguous, unsupported engine, unavailable permission/Query Store, malformed XML, oversized XML and cancellation. Do not map any of them to an empty successful plan. Existing parser tests cover invalid/malformed/oversized source documents, but not future catalog error mapping.
5. **Evidence scope:** All outcomes here are source inspection and offline synthetic/static fixture checks. No runtime model-token savings, recurrence, live deployment behavior, catalog permissions or live database acceptance was measured.
