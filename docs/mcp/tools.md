# MCP tools

## Tools

Exactly 9 tools are registered explicitly by name when operation annotations are off; the opt-in annotation tool makes 10. No assembly scanning is used, so adding a public method can never silently widen the surface. A regression test keeps the serialized `tools/list` catalog below 36 KiB; this test ceiling is not a runtime protocol or response-size limit.

Descriptions are engine-scoped at startup. A fixed-scope process renders its resolved target's native setup and query safety guidance into the `query`, `measure` and `compare` descriptions; request scope is SQL Server only and renders SQL Server guidance. The full SQL Server table IO identity rule is available as `engineGuidance.tableIo`; `measure` and `compare` point to it. The text that holds for both engines (setup runs once per session, setup locals do not carry into measured SQL) is common. Capabilities for a CLI profile carry the same guidance as `engineGuidance`; for SQL Server read-only session/control-flow admissions and denials, that guidance is the interface contract and the [README Safety contract](../../README.md#sql-server-read-only-session-and-control-flow) is the human reference. Descriptions never change what executes or is authorized.

Tool and argument descriptions expose setup/session rules, mutually exclusive parameter-set inputs
and saved-plan selection at the call site. Use capabilities for runtime configuration, and the result's
status, omissions, continuation and evidence gaps to judge whether the returned evidence is complete.
The seven projected tools accept `maxCellChars` (0..4096, default 2048), matching CLI agent output's `--max-cell-chars` option.
Parameter-set files are bounded to 16 MiB per file and 32 MiB total raw file bytes per call. `sqlharness_capabilities` reports these byte counts as `parameterFileIngress.maxFileBytes` and `parameterFileIngress.maxTotalBytes`, separately from the unchanged 32 MiB `materializedParameterBytes` limit; larger raw JSON admission does not increase the allowed decoded/materialized SQL parameter data.

When enabled, `operationAnnotations: true` reports that this process accepts call-time labels/keep flags and returns operation references for eligible journal rows. Fixed scope includes the selected profile's effective mutation mode and writer presence; request scope reports those fields for each allowlisted profile without changing `allowedProfiles` or selecting an active profile. `includeDiagnostics: true` adds local counts and directory existence flags. Never disclosed: credentials, environment values, the dashboard token, unrelated filesystem paths, or profiles outside the allowlist. Dashboard reachability means a validated live lock/PID publication is present; capabilities does not make a database connection or network probe. |
| `sqlharness_query` | Bounded query passing the engine's static visible-effects checks, with timeout and row cap. Optional `resultSetOrdinals` (nullable integer array, at most 64 unique non-negative source ordinals) selects query response sets after execution; null preserves the existing response, `[]` selects none, and emitted sets retain their original ordinals. Values are checked against the executed response. Opted-in successful results add `sourceResultSetCount`, normalized `selectedResultSetOrdinals`, and uppercase SHA-256 `queryHash` of the exact resolved SQL UTF-8 bytes. Selection bounds only response projection, not SQL execution or row materialization. SQL Server session/control-flow admissions and denials are included in the engine guidance appended to the `query`, `measure`, and `compare` descriptions and in the `engineGuidance` capability. Optional `dryRun: true` (see below). A returned query duration describes that query response and is not benchmark evidence. Estimated rows are estimates; `actualRows` are observed and `executions` counts operators. Dry-run reports validation passed and execution not run. No persistent-mutation flags are offered on this path; hidden effects beyond the text are limited only by the DB account role prepared outside SQLHarness. |
| `sqlharness_mutation` | Submit a persistent change through the profile's dashboard mutation policy. Optional `dryRun: true` validates the exact request offline and does not connect, store an artifact, or ask for approval. The call waits for a terminal result; report every status except `success` and never retry or switch transports. |
| `sqlharness_measure` | Measure one query across repeats. Accepts exactly one of `parameterSets`, `parameterSetFiles`, or `matrix`, plus optional setup. Parameter-set files are limited to 16 MiB each and 32 MiB total raw bytes per call. Each parameter set runs on its own session with setup bound to that set. Sets run in order; the first failure stops the run and completed sets are retained. Optional `dryRun: true` checks the exact sets offline. TVP and list parameter sets have no `valueHash`; their values are excluded from unkeyed hashes. |
| `sqlharness_compare` | Compare baseline versus candidate with the CLI equivalence rules. With `compareContext.requireContext: true`, requires textual `subject` and optimization `scope`; request-scoped calls also require `target`. With it false, the two context fields are absent from the schema and rejected, while request-scoped `target` remains required. Accepts exactly one of `parameterSets`, `parameterSetFiles`, or `matrix`; parameter-set files are limited to 16 MiB each and 32 MiB total raw bytes per call. Each set uses one connection and setup runs once on that connection. Output retains an ordered cell inventory with set labels before optional per-cell detail. Optional `dryRun: true` checks the exact sets offline and returns validation status, aggregate risk tier, and the setup/baseline/candidate safety classifications without executing them. A comparison `pass` means the configured elapsed-time regression condition was not met; it does not establish an improvement. Observed result equivalence follows the selected ordered, multiset or set rule and does not establish equivalence in the application's domain. Optional `compareNullability` (boolean, default `false`) also requires matching column nullability (`allowNull`) for equivalence; it is rejected with `compareResults: "off"` (`compareNullability requires compareResults ordered, multiset, or set.`). Results always carry `compareNullability`, `nullabilityEquivalent` (`true`, `false`, or `null` when not comparable or unavailable, including when the provider reported no nullability for a compared column; that column's `allowNull` elsewhere still reads `true`) and `mismatchReason` (`"nullability"` only when strict mode alone caused the mismatch) in the equivalence object, including matrix cells. Cell-limit clipping and truncation indicators still apply; the input document is never returned or persisted. Errors stay credential-filtered. |

The call itself is journaled without a reference and cannot be an annotation target. |

### Operation annotations

Set `journal.operationAnnotations: true` in `~/.sqlharness/config.json` to expose optional `label` and `keep` inputs on `query`, `measure`, `compare`, `watch`, and `snapshot`, and to register `sqlharness_annotate`. The setting defaults to false, requires `journal.enabled: true`, and is frozen at process start. Restart the MCP server and reconnect the client after changing it. With the setting off, the extra inputs, tool, result `operationRef`, capability member, and annotation wording are omitted.

An enabled eligible call returns its opaque `operationRef` only when it has a journal row. The reference is reserved within the result byte budget and also survives the minimum-size fallback. `sqlharness_annotate` accepts 1..20 references. Authorization uses the caller's MCP session and exact transcript links: when the caller resolves to a conversation, a target must link exactly to that same provider and conversation, or be in the caller's MCP session with no exact link elsewhere. If the caller is unresolved, the target must be in the caller's MCP session and have no exact link to another conversation. Inferred membership never authorizes access. The caller's provider and conversation tuple must match exactly. Labels are plain text of up to 120 Unicode code points; control characters and line breaks are rejected. Agent labels and keep flags are stored whenever this setting is enabled, independently of `journal.storeSensitive`; they are separate from the owner's star and note. Keep/star are markers, not retention pins: normal journal retention can delete the operation and its annotations. `sqlharness_annotate` defaults to `responseDetail: "receipt"`, returning one ordered result per input: successes contain `operationRef`, `status`, `tool`, and `keep`; unavailable references contain only `operationRef` and `status`. Receipts omit labels and fit the minimum 4096-byte result budget for every valid batch of up to 20 items. Choose `responseDetail: "full"` to include resulting labels. Optional `maxResultBytes` uses the standard 4096..1048576-byte range and is capped by the process ceiling. The selected complete response is checked before commit; an oversized full response rolls back every annotation and reports the effective and maximum allowed bytes with receipt or a larger allowed budget as the next action. The dashboard's **Named operations** view and owner annotations remain available when the agent-facing setting is off.

For example, request full detail explicitly when the resulting labels are needed:

```json
{"items":[{"operationRef":"0123456789abcdef0123456789abcdef","label":"reviewed","keep":true}],"responseDetail":"full"}
```

At a 4096-byte operator ceiling, an oversized full response returns an error like `The complete annotation response exceeds the effective 4096-byte result budget (maximum allowed 4096 bytes). use responseDetail 'receipt'. No annotations were changed.` The transaction rolls back; retry with the default receipt to apply the same update without label echoes.

Tool annotations are conservative local-effect hints only: benchmarks write artifacts, and snapshot capture writes data, so those tools never claim read-only. Hints never replace policy enforcement.

### Parameters and dry runs

Parameter names may include one optional leading `@` (for example, `Name` and `@Name` bind identically). Reports use the canonical `@Name` form. This applies to typed parameters, all three set forms and `.sqljson` parameter-set files. The `@` is accepted only once; the remaining name must start with a letter or underscore and contain only letters, digits or underscores.

Both benchmark tools accept the same mutually exclusive forms: `parameterSets` is an inline array of `{name, parameters: [{name, type, value}]}`, `parameterSetFiles` is an array of `.sqljson` paths under a configured input root, and `matrix` is `{name, type, values}` for one parameter. Set names follow the safe-label rule. Each form accepts 1–32 cases; an explicitly empty collection is invalid. Each set must use the same parameter names and declared type, size, precision and scale; unsized types such as `nvarchar` may infer different bound value sizes. A missing or unexpected name, shape mismatch, fixed-parameter overlap, or invalid set label is rejected by the shared Core validation. Set values are typed strings or JSON null. Matrix commas, empty strings and typed NULL remain distinct. The CLI `--param-set` and `--matrix` text grammars are unchanged. Calls above 32 cases must be split into separate calls, and a singleton remainder is supported.

Set `dryRun: true` on `sqlharness_query`, `sqlharness_mutation`, `sqlharness_measure` or `sqlharness_compare` to validate the exact call, setup and selected parameter-set form, including every inline set or matrix value; parameter-set files are included too. A successful response labels validation as passed and execution as not-run, includes the aggregate risk tier, and retains each setup/query or setup/baseline/candidate safety classification where applicable. It is the same check as CLI `--dry-run`. A mutation dry run returns before database connection, artifact storage or approval request. Its checks, report fields and limits are in the dry-run rule of the [README Safety contract](../../README.md#safety-contract).

Calls that reach Core, including dry runs, are journal operations. A dry run's displayed response contributes to workflow output bytes and call counts, while its `dry_run` flag keeps it out of database-execution counts and it cannot be a comparison baseline. Capabilities discovery, `tools/list`, input tokens and final chat are outside the output-cost coverage. The `single-measured-execution-output` baseline includes the first measured result/messages for each variant and parameter set in the producer; it excludes warm-ups, later repeats, and plan XML. The dashboard joins artifact reads to producers through exact opaque operation references. A top-level call has an `operation_ref`; an artifact read has its own reference and sets `parent_operation_ref` to the producer. Missing references on old rows mean unavailable provenance, never a path or timestamp guess. Schema v7 adds nullable `operation_ref` and `parent_operation_ref` plus `dry_run` (`NOT NULL DEFAULT 0`). It reuses the `raw_bytes` and `emitted_bytes` columns introduced in v3; stored byte values remain intact. Existing rows have null references and `dry_run = 0`, while legacy token columns remain readable; no historical provenance is inferred or backfilled. The dashboard labels unreferenced history `legacy-artifact-volume` and excludes it from comparable workflow totals. Output-byte measurements are authoritative; displayed tokens use `ceil(UTF-8 bytes / 4)` and remain estimates, not actual savings or provider tokenization. See [workflow output cost](../../README.md#activity-journal-and-workflow-output-cost) for coverage and comparison semantics.

## Persistent mutations

Use `sqlharness_mutation` for persistent DML, DDL, privilege changes and opaque statements accepted by the static classifier. Its argument parity with CLI `mutation` is intentional; inspect the tool schema for exact field names, bounds, source selection and output rules. The dashboard reads current profiles and operator settings at submission and rechecks them before execution. A profile without an explicit mode inherits the global default; its writer is configured independently and must exist for execution. `never` rejects persistent changes, `operator` asks for approval, and `yolo` executes only the `dml` tier without asking; `schema`, `privilege` and `opaque` always require a click. A `yolo` profile labeled `prod`, `production` or `staging` needs explicit `acknowledgeProductionYolo: true`. The click-only verification and 30..600-second approval timeout are operator policy; WebAuthn is deferred to [plan 078](../../plans/078-mutation-approval-webauthn.md).

The call waits for a terminal result. `success` is exit `0`; rejections and approval outcomes (`mutations_disabled`, `approval_unavailable`, `approval_timeout`, `denied_by_operator`, `busy`, `not_a_mutation`, `principal_protected`) are exit `2`; `database_mismatch` is exit `4`; `failed` and `outcome_unknown` are exit `5`. A timeout, cancellation, failure or unknown outcome does not establish that no SQL ran. Do not retry or use another transport. An approval is consumed before SQL is sent and executes at most once. The broker rechecks current target and policy when execution begins.

Capabilities reports the global default mode, click verification, approval timeout and whether the dashboard's live lock/PID publication is present. Fixed scope also reports the selected profile's effective mode and whether a writer is configured. Request scope keeps `allowedProfiles` unchanged and reports those same two fields per allowlisted profile; it does not select one active profile. Capabilities never returns credentials, environment values, tokens or profile variables.

The `query` tool remains a bounded static-visible-effects path with no persistent-mutation switches. Every non-approved PostgreSQL command runs in a `READ ONLY` transaction; the server rejects persistent table and sequence writes (SQLSTATE `25006`, safety exit `2`). PostgreSQL TEMP setup is the exception: it runs outside that wrapper and static validation cannot inspect user-defined function bodies, so review setup SQL and use a least-privilege role. The classifier denies known administrative effects but cannot prove arbitrary user functions harmless. Session-local temporary objects follow the same Core rules as the CLI. Snapshot capture stores under a fresh name only. SQL Server's allowlisted read-only `SET` options and session/control-flow constructs are described in engine guidance and the README [Safety contract](../../README.md#sql-server-read-only-session-and-control-flow). Plain `SET @v = <expr>` to a scalar local declared earlier in the batch is also allowed; compound, cursor and member-variable assignments remain denied. Parameterized setup splits at its first parameter reference; temp creation must precede it, and setup variables do not cross into measured batches.
