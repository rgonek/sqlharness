# MCP runtime

## Result envelope, errors, and budgets

Every tool returns a schema version 3 MCP agent envelope (`schemaVersion`, `status`, `result`; `error` and `truncation` only when populated) in one text block containing compact JSON. The CLI `--output agent` envelope remains schema version 2 and keeps `command` and `exitCode`. Comparison mode, watch exit reason and snapshot verdict are documented strings on the MCP path (`ordered`/`multiset`/`set`/`off`, `condition-met`/`unchanged`/`max-duration`, `stored`/`identical`/`different`).

When `journal.operationAnnotations` is enabled, eligible journaled `query`, `measure`, `compare`, `watch`, and `snapshot` results include an `operationRef` in the v3 envelope. The field is absent if no journal row was created, and the adapter reserves its bytes so it remains present in compact and minimal error envelopes. With the setting off, the v3 result bytes remain unchanged.

- Statuses: `success`, `partial` (failed matrix-cell batch), `error`, `watch_max_duration` (exit 7), and `snapshot_differences` (exit 8). The two controlled outcomes are valid results with `isError=false`; only failures set `isError=true`.
- `mutation` returns its broker status directly: `success`, `mutations_disabled`, `approval_unavailable`, `approval_timeout`, `denied_by_operator`, `busy`, `not_a_mutation`, `database_mismatch`, `principal_protected`, `failed`, or `outcome_unknown`. Only `success` has exit 0. Every other status is an error result; stop and report it, and never retry the call or switch transport/profile. `approval_timeout` and `denied_by_operator` mean the write was not executed. `outcome_unknown` means execution may have started but completion could not be confirmed; inspect dashboard history before taking any further action.
- Budgets are enforced on the UTF-8 bytes of the single text block the model reads, including JSON escaping. Each call defaults to 65536 bytes and accepts 4096..1048576, bounded by the process ceiling; a call may raise or lower its budget. The tools/list catalog budget is 32768 bytes for exactly 9 tools, or 10 when operation annotations are enabled. The seven projected tools accept `maxCellChars` from 0..4096 characters, defaulting to 2048; truncated results report the applied value as `truncation.maxCellChars`. This matches CLI `--output agent --max-cell-chars` (plan 060 parity).
- `sqlharness_artifact` uses the same per-call `maxResultBytes` range, default and process-ceiling cap. Its optional `pageSize` is a source-window limit for `matrix-cells`, `operators`, `statements`, or `plan` (1..512; omitted defaults are 32, 32, 128, and 128). The source window does not override the response-byte budget: projection emits only complete records that fit and continuation advances by the records returned. See [MCP artifacts](artifacts.md#artifacts) for section selection and recovery behavior.
- JSON is never cut mid-document: every report uses the same detail ladder `unbounded, 128, 64, 32, 16, 8, 4, 2, 1, 0` until the envelope fits. MCP reports `truncation.omittedItems` and `truncation.maxCellChars`; it does not expose the internal detail-ladder setting. CLI agent output also reports `truncation.detailLimit`. If even the minimum envelope does not fit, SQLHarness emits `output_budget_too_small`.
- Query fallback priorities (`sqlharness_query`; the CLI agent output uses the same projection). Query values are compacted before the final budget check: the resolved database and CLR `valueType` aliases are retained, while the rest of `target`, `resultHash`, and `rawFootprint` are omitted. `valueType` describes the CLR value and does not infer a SQL type. Above level 0 every result set and column stays, emitted rows keep all cells aligned with the full schema, and each set emits a leading row prefix. A set with more rows than the limit is emitted whole when complete rows fit a conservative reserve: one third of the budget minus the rowless shell (all set inventories and schemas), assigned by complete-row cost then ordinal, whole set or nothing. Other sets are sampled, so a small summary set is not cut to a wide detail set's sample. Messages are capped at the same limit; dropped messages count in `truncation.omittedItems`. Clipped strings remain prefixes with UTF-16 surrogate pairs intact; binary cells whose base64 exceeds the cell limit use `{byteLength, base64Prefix, truncated}`, and shorter binary cells remain plain base64. Every clipped retained cell has a `clippedCells` entry with its set-local zero-based row and column, original and returned lengths, and unit (`utf16-code-units` or `bytes`); omitted rows have no cell entries. At level 0 the fallback spends a conservative budget share (the final serialization remains authoritative) in this order: inventories for leading sets that fit; whole schemas, cheapest first then ordinal; whole rows for retained schemas, cheapest set first then ordinal; leading column prefixes for schemas that did not fit whole, with no rows; then leading row prefixes for full-schema sets. Small summary sets therefore keep their schemas and rows ahead of a wide detail set. Per-table read details are ordered by descending median reads, then descending maximum, then table name.
- `logicalReadsByTable` keys are table identities, so the cell limit never shortens them, including when `maxCellChars` is zero. The response budget still applies: if an entry cannot fit, projection omits the complete entry and counts it in `truncation.omittedItems`.
- Query results use the compact projection before the final budget check. Column `valueType` names CLR values (for example, `System.DateTime` becomes `dateTime`); it does not infer SQL types. The resolved `database` is retained while the rest of `target`, `resultHash`, and `rawFootprint` are omitted. A clipped retained cell stays a string prefix or the existing binary-prefix object, and `clippedCells` records its zero-based row and column within that result set, original and returned lengths, and unit (`utf16-code-units` or `bytes`). Omitted rows have no cell entries. Empty messages and zero omission counters are omitted; `recordsAffected: 0` and empty-result columns remain present. The shared query projection keeps result-set ordinals and column order, and its row/detail fallback follows the same priorities described here.
- Nonzero accounting fields identify trailing omitted result sets, columns, and rows. `omittedRowCount` is the source omitted count plus rows not emitted: `rows.length + omittedRowCount` equals the source rows plus the source omitted rows. `sourceOmittedRowCount` and `projectionOmittedRowCount` split that total when their respective counts are nonzero; zero omission counters are omitted. `truncation.omittedItems` is an aggregate: an omitted result set counts 1, each omitted column counts 1, each omitted row of a kept set counts 1, and clipped cells and dropped messages count too. Explicit per-set and per-query counts give the authoritative row/column/set accounting; nothing implies a set, column or row exists unless the counts say so. Watch results use the same compact row/schema/clipped-cell representation; `omittedPolls` is history omitted by the watch source, while `omittedEmittedPolls` counts emitted history omitted by response projection.
- `compare` over any set form keeps an ordered cell inventory containing each cell index, artifact id and `setName`; matrix cells also carry displayed `parameterValue` (JSON null only for a typed NULL). Cell reports include the set-only bound parameters. `detailLimit` controls optional per-cell diagnostics and never removes cell identity. If the inventory itself exceeds the response budget, `matrixArtifactId` and a continuation cursor fetch the remaining cells through the scope-owned `matrix-cells` section; each page uses the same cell schema. Filesystem paths stay out of the projection.
- Every output replaces the resolved profile password and Azure SQL access token fetched for the operation. Other text, including caller SQL quoted in server errors, stays readable.

## Concurrency, deadline, cancellation, and progress

Read and analysis tool calls run concurrently, across request scopes too; each call builds its own operation and keeps its own deadline and cancellation. The mutation broker allows one pending request per MCP session; approving concurrent writes to the same profile returns `busy`. SQLHarness does not serialize benchmarks: any other load on the server (another call, another session, a colleague, a tester) can disturb a measurement, as it always could. Run `measure` and `compare` while the server is quiet, and repeat a comparison before trusting a close verdict. Every execution is bounded by the process time budget (default 900 s, range 1..86400 s) through a linked deadline that always reaches Core.

Cancellation propagates to connection, execution, reads, delays, and artifact writes. Closing the process (host shutdown) or stdin EOF cancels an in-flight call, which reports a stable cancelled result (`isError=true`), never the natural watch-deadline exit 7. Cancelling one call leaves every other call running. For `mutation`, cancellation while waiting for dashboard approval removes the pending request and does not execute it. Once approval has started execution, a client disconnect or deadline can leave the result unknown; do not retry, and check dashboard history for the final recorded outcome.

Progress notifications go out at most once per second per call, only when the client supplied a progress token, and carry only the command and stage: never SQL, parameters, or rows. While a mutation waits for dashboard approval, it reports `awaiting_approval` at most every five seconds; this does not indicate that execution has started. Watch does not emit NDJSON on the MCP path; NDJSON stays a CLI-only surface.

The `sqlharness_capabilities` result reports `defaultExecutionTimeoutSeconds` in fixed and request scope. It is the process's configured SQL timeout fallback from `execution.defaultTimeoutSeconds` in `~/.sqlharness/config.json` (default 30 seconds); calls can override it with `timeout`. MCP snapshots configuration at process start, so after changing the setting restart `mcp serve`, reconnect the client, and request capabilities again. CLI commands read the setting when invoked, so a new command uses the saved value.

The activity journal records why a call was cancelled: `client` (the client sent
`notifications/cancelled`), `shutdown` (stdin closed or the host stopped), or
`deadline` (the call time budget ran out).

### Troubleshoot a timeout

Use the response shape to identify which limit ended the call. A SQL command timeout returns a SQLHarness envelope such as:

```json
{"schemaVersion":3,"status":"error","result":null,"error":{"code":"sql_execution_failed","phase":"sql","message":"<provider timeout message>"}}
```

The message is provider text and can vary. `timeout` controls an individual SQL command and stays within 1..300 seconds; when omitted, the process uses `execution.defaultTimeoutSeconds`. The value does not extend the MCP call budget.

When SQLHarness's process or per-call operation budget expires, the server cancels the call and returns its stable cancellation envelope:

```json
{"schemaVersion":3,"status":"error","result":null,"error":{"code":"cancelled","phase":"execution","message":"The operation was cancelled."}}
```

**Synthetic client-wait case:** the external client reports a local `tools/call` wait timeout and receives no SQLHarness tool response. There is no SQLHarness envelope to inspect; server completion is **UNKNOWN**. The client may have stopped waiting while the server was still working, or cancellation may have reached SQLHarness; the client timeout alone does not establish which happened. SQLHarness does not set the external client's call ceiling. Keep using the existing stop and retry rules for the tool, including the mutation rule above.

The separate `connection.timeoutSeconds` setting bounds SQL connection establishment and driver-managed authentication; it applies before SQL command execution. Azure CLI token acquisition has its own budget. For either SQLHarness setting, saving configuration does not update a running MCP process: restart `mcp serve`, reconnect the client, then request `sqlharness_capabilities` to confirm the values loaded by that process. Whether a particular client automatically reloads its configuration is client-specific and is not established here.

## Stdout and stderr

Stdout carries only protocol frames. Logging goes to stderr. SDK entries sent to stderr are limited to `Warning`, `Error`, and `Critical`; their message and exception text are rendered through `SecretRedactor` with the resolved profile credentials, while category, level, and numeric event ID remain available. This replaces known credentials; other caller-provided SQL or parameter data in a diagnostic may remain visible. SQLHarness may also write stderr lines for a pre-handshake startup failure (exit 2), an unexpected transport failure (exit 1), a failed detached-dashboard launch, or a roots diagnostic naming a count (`kept N of M`) or failure class (`roots/list timed out`, `roots/list failed (<ExceptionType>)`). Clean shutdown on EOF or cancellation exits 0. Tool calls that reach the SQLHarness module (query, mutation, measure, compare, watch, snapshot, plan, artifact) are recorded in the local activity journal with the client's `clientInfo` name, version and title, the negotiated protocol revision, and a raw token estimate. Credential-redacted error messages are stored by default and may include caller-supplied SQL or data values; SQL text and full plans are stored only when `journal.storeSensitive` is enabled. The `sqlharness_capabilities` response reports plan availability as `stored` or `plans not stored` under `limits.activityJournalStorage.planStorage.state`; the dashboard exposes the same gate for its plan viewer. The MCP handler records emitted bytes from the UTF-8 text block the model reads after applying the result budget. The `ceil(bytes / 4)` value estimates output size; it is not actual model tokenization. Historical raw-only MCP rows stay unavailable and are not backfilled. Each recorded call also keeps allowlisted `tools/call._meta` labels: the client's call id (Claude Code `claudecode/toolUseId`, Codex `callId`), opencode `ai.opencode/sessionID` as the agent session id, and from Codex `x-codex-turn-metadata` the model, reasoning effort, agent session id, turn id, turn trigger and thread source; other `_meta` keys are never stored. `sqlharness_capabilities` is not recorded; journal diagnostics go to stderr only, and journal failures never change a tool result.

With `dashboard.autoStart: true` in `~/.sqlharness/config.json`, a validated startup (an invalid startup configuration never launches anything) also launches `sqlharness dashboard --background` as a detached process that inherits none of the server's standard handles, with the SQLHarness home as working directory, when no dashboard is running for that home, and starts one journal retention pass in the background (it does anything only with `journal.retention.enabled: true`). Both happen before the transport starts, neither writes to stdout, and a failed launch writes one line to stderr and never changes the server's behavior. The MCP client still sees EOF when the server exits, while the dashboard keeps running until it idle-exits after `dashboard.idleShutdownHours` (default 8). Known limitation: the dashboard is not placed in a new session or process group, so Ctrl+C or SIGHUP delivered to the client's process group (or closing its console on Windows) also stops it; the next `mcp serve` relaunches it.

## Context cost

Emitted bytes count the UTF-8 bytes of the single text block the model reads, including JSON escaping. Token estimates reuse the Core `OutputFootprint.EstimateTokens` heuristic (`utf8-bytes-div-4`: bytes divided by four, rounded up). Byte counts are not token counts; do not report bytes as actual tokens.

Scenario comparison counts the whole MCP run: tools/list discovery plus the call plus any follow-up artifact read, against the CLI agent output for the same outcome. Discovery stays a separate visible cost and is never folded into saved data. The offline comparison asserts only that the scenario total exceeds the single call and that each side fits its budget (call within 65536 bytes by default, discovery within 32768 bytes). MCP is not promised to be cheaper per call.

## Evidence scope

Executed: published single-file stdio smokes for both fixed and request-scoped modes on the native win-x64 runner. The request-mode proof uses two synthetic profiles and exercises per-call validation; it does not register or launch the server through an MCP client's private configuration. The MCP test project passed its offline tests, with live-database and non-native RID cases skipped. The full solution offline run exposed two failures in `SqlHarness.Tests`: one output-size fixture mismatch also reproduced on the request-scope implementation's base commit, and one transient artifact-directory `IOException` that passed on focused rerun. The cost comparison above comes from offline tests on synthetic data, without opening a database.

Not executed: published-binary runs on linux-x64 and osx-arm64 (binaries build; the per-RID smoke tests Skip without native runners), live SQL Server and Postgres stdio drives (Skip without explicit disposable-database authorization), or private client registration/startup. A stdio driver is protocol evidence, not actual-client evidence. Live scenarios, client registration, and additional RIDs must not be reported as passing.
