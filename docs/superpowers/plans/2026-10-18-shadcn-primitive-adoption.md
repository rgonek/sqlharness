# shadcn Primitive Adoption Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the five shadcn primitives the dashboard was missing and replace every hand-written approximation of them — 14 `<select>`, 10 native `<details>`, 3 `type="checkbox"`, 2 `<textarea>`, 2 radio inputs and 1 hand-written dialog trigger.

**Architecture:** Each task takes one primitive and the sites that use it, so a reviewer can approve the checkbox conversion while rejecting the accordion conversion. Components in `src/components/ui/` are generated by `shadcn add` and never hand-edited. Conversions are mechanical except where the spec names a specific hazard: the `ProfileDimensionsPanel` tri-state select, the per-dimension default-open accordion, the `OptimizationSection` chained selects, and the `StatsPage` dual accessible name.

**Tech Stack:** React 19, TypeScript, Vite 8, Tailwind v4, shadcn/ui on Base UI primitives, Vitest, Testing Library, `userEvent`.

**Spec:** `docs/superpowers/specs/2026-10-18-shadcn-cli-and-primitive-adoption-design.md` — read Parts 2 through 7 and the Risks section before starting.

**Depends on:** `docs/superpowers/plans/2026-10-18-shadcn-cli-restoration.md` must be complete. That plan restores the CLI as a `devDependency` and repoints `src/index.css` at `shadcn/tailwind.css`. Without it, `shadcn add` and every generated component's `data-*` variants break.

## Global Constraints

- Base UI primitives only. Any component importing from `@radix-ui/*` is wrong for this repository.
- Generated files in `src/components/ui/` are not hand-edited. If a generated file needs a change, fix it by changing `components.json`, not by editing the file.
- No restyling beyond what a site already does. Preserve each site's existing height, width and background classes through `className` where the generated variant does not match, and change nothing else.
- Copy is user-visible and frozen. No control's label text changes.
- `optimization/VersionTable.tsx:21,22` keeps its native radio inputs. They render inside `<td>` cells grouped only by `name`, with no fieldset, and `RadioGroup` cannot span table rows. Do not convert them.
- Domain components stay as they are: `PlanTree`, `SessionTable`, `OperationTable`, `SqlBlock`, `Kpi`, `VariantPanel`, `BrandLogo`.
- Audit criterion after every task: `npm --prefix src/SqlHarness.Dashboard/ui audit --omit=dev` reports no findings other than the two pre-existing `dompurify` advisories through `monaco-editor`.

## Shared Conversion Patterns

Use these in every task below. They are stated once here so the tasks stay short.

**Adding a primitive.** From `src/SqlHarness.Dashboard/ui`:

```bash
npx shadcn@latest add <names>
```

Then immediately:

```bash
git status --short
```

Expected: only new files under `src/components/ui/`, no modification to `src/index.css`, and `shadcn` absent from `dependencies`. If `index.css` changed, revert that line. If `package.json` gained `shadcn` under `dependencies`, run `npm uninstall shadcn` — the CLI is a `devDependency` and must stay one.

**Accessible name.** Prefer an explicit `<Label htmlFor={triggerId}>` plus `id={triggerId}` on the control over a wrapping `<label>`. Base UI's `Select` root renders a `<button>`, which is a labelable element, but the explicit form does not depend on that.

**Checkbox.** `checked` and `onCheckedChange`, not `onChange`. The root already carries `role="checkbox"`, so existing `getByRole("checkbox", { name })` queries keep resolving unchanged.

**Select.** The generated `Select` is a button trigger with `role="combobox"` presenting options in a portal. It is **not** a native `<select>`. See "Rewriting select assertions" below before touching any test.

**Accordion.** The generated accordion renders no `details`, no `summary` and no `open` attribute. Existing tests that use `.closest("details")`, `not.toHaveAttribute("open")` or filter on `tagName.toLowerCase() === "summary"` must be rewritten. See "Rewriting disclosure assertions" below.

**After every task:** `npm run typecheck && npm run lint && npm test`, then commit.

## Rewriting select assertions

Two distinct rewrites. Both are mechanical; neither may weaken what is asserted.

**Choosing an option.** `userEvent.selectOptions(element, value)` throws on anything that is not a native `<select>`. Replace with:

```ts
await user.click(screen.getByRole("combobox", { name: "Case" }))
await user.click(screen.getByRole("option", { name: "…" }))
```

If multiple options share a visible label, scope with the option's own text and assert the resulting trigger text afterwards rather than relying on the option being uniquely named.

**Asserting a value.** `expect(combobox).toHaveValue(x)` asserts a native select's `value` property. On a trigger, assert the rendered value instead:

```ts
expect(screen.getByRole("combobox", { name: "From version" })).toHaveTextContent("v3")
```

Where the trigger shows a placeholder rather than the value, assert the chosen option by its visible label. Where the test needs the machine value rather than the label, assert through the application's own state or the network call it makes, as `SessionVersionDiff.test.tsx:68,81,82` already does.

**`fireEvent.change` on a select** must also become click-then-click. There is one such site, `CompareDetail.test.tsx:65`.

**Portal scoping.** Options render in a portal under `document.body`, so `screen` resolves them but `within(container)` does not. Any assertion scoped to a container must move to `screen`, or the option lookup must be re-scoped.

## Rewriting disclosure assertions

Replace assertions about the `<details>` element with assertions about observable behavior:

| Old | New |
|---|---|
| `expect(x.closest("details")).not.toHaveAttribute("open")` | `expect(screen.getByRole("button", { name: x })).toHaveAttribute("aria-expanded", "false")` |
| `within(x.closest("details")!).getByText(y)` | open the panel with `await user.click(...)`, then assert with `screen` |
| `getAllByText(t).find(el => el.tagName === "summary")` | `screen.getByRole("button", { name: t })` |

Confirm per component whether accordion content stays mounted while collapsed, and whether it remains in the accessibility tree. Do not assume parity with `<details>`. If an assertion only passes because closed content is hidden, say so in the commit.

## Review Focus

Failure modes the spec implies that a passing test suite would not catch.

1. **"All values" is no longer selectable** in the `ProfileDimensionsPanel` dimension filter, because the tri-state maps `undefined` to `""` and the Base UI convention for "no value" is `null`. A person using the filter to clear a selection and get all values back would find no way to do it. Pin: Task 9, Step 4.
2. **A dimension breakdown starts collapsed** in `ProfileDimensionsPanel`, where every `<details>` currently carries `open` and all dimensions start expanded. Pin: Task 7, Step 4.
3. **Changing the conditions group leaves a stale scope selected** in `OptimizationSection`, whose scope reset at line 69 also clears `a`, `b`, `case` and `agg`, not just `scope`. Pin: Task 10, Step 3.
4. **A closed accordion's content is still reachable by a screen reader** in a way a `<details>` was not, or is silently removed from the accessibility tree and cannot be found at all. Pin: Task 6, Step 5.
5. **The matrix column select no longer disables the axis currently used as the row**, because `disabled` on an option must be carried onto the generated item. Pin: Task 9, Step 5.
6. **The nested "More" disclosure in `TableIoComparison` collapses its parent** when opened, since it now sits inside an accordion item. Pin: Task 6, Step 6.
7. **The `StatusBadge` dialog opens but its tooltip no longer does**, or neither opens, after the trigger swap contends with Base UI's `mergeProps` over `role`, `aria-haspopup` and `ref`. Pin: Task 5, Step 3.
