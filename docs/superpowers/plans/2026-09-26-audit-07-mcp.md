# MCP adapter Implementation Plan

**Status (2026-10-08):** DONE — 975da6a..c962646 (2026-09-28), documentation `docs/mcp.md`; later fixes in `plans/001`–`012`. The checkboxes below were not ticked during execution.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Expose the local SQLHarness MCP server after completion of audit plans 01–06, with shared Core, a safe scope and limited response cost.

**Architecture:** `sqlharness mcp serve` runs a stdio host from the SqlHarness.Mcp library. The adapter maps typed arguments to existing Core operations and the shared agent projection; it does not run the CLI or SQL through a shell.

**Tech Stack:** .NET 8, the official ModelContextProtocol C# SDK (a stable compatible version pinned in T1), System.Text.Json, xUnit. No HTTP/SSE in v1.

**Spec:** [MCP adapter design](../specs/2026-09-26-mcp-adapter-design.md), [whole-program order](2026-09-26-audit-roadmap.md).

## Global Constraints

- **Implement after 01–06.** The design results of 06/T4–T5 are not implemented features. The later [plan 08](2026-09-26-audit-08-windows-approval-tray.md) adds the Windows tray and approvals; it does not broaden the scope of the first MCP version in this plan.
- One process has one closed profile and vars fixed at startup; a tool does not change the target or credentials.
- No persistent mutations and no unsafe-direct in MCP v1. Session temp only in accordance with Core.
- One active DB operation; the other receives BUSY. Scope is not a DB session and does not share temp between tools/call.
- At most 11 tools, tools/list catalog ≤32 KiB; CallToolResult by default ≤16 KiB including both representations.
- Param-set only as existing .sqljson files; file input only in the operator's explicit roots. No publishing of raw plans, SQL texts and snapshot cells through artifact.
- Stdout is protocol only; stderr without secrets. No separate SQL validation in MCP.
- New SDK versions do not justify an implicit change of the framework or repo standards.

## Review Focus

- Changing targets.json or a smuggled target in tools/call: T2.
- Unknown fields, type overflow and invalid values in a message: T3.
- Symlink/traversal and a plan with literals: T3–T4.
- Dual JSON representation, escaping and a large tools/list: T4.
- Cancellation, EOF, concurrent calls and single-file publish: T5–T6.

## T5 — concurrency, cancellation and lifecycle

**Files:** McpExecutionGate.cs, McpHost.cs, McpOperationMapper.cs; new `McpLifecycleTests.cs`, `McpCancellationTests.cs`.

**Interfaces:** the gate recognizes DB operations and grants a single active execution; others get a stable BUSY code. The process time budget is 900 s by default, configurable 1..86400; a call can only lower it.

- [ ] Test two concurrent DB calls: one executed, the other BUSY without queueing. A local capabilities file works during the benchmark. No sharing of reader/temp/parameter state between calls.
- [ ] Test cancellation during connect, setup, benchmark repeat, sidecar, watch delay and artifact write. The next call works after cleanup; partial artifacts conform to the Core contract, with no success path before publish.
- [ ] Test client EOF and process shutdown: the linked token reaches Core, the session is disposed, there is no hanging watch. Do not report a cancelled call as a natural watch exit 7.
- [ ] Progress only for the token received, limited to 1/s and without a SQL payload. No NDJSON watch on stdout; only protocol notifications and the final tool result.
- [ ] Test the annotations array: do not declare readOnlyHint/idempotentHint contrary to snapshot/artifact/gain writes; hints do not decide access.
- [ ] Run the new tests with a controlled clock, without sleeps dependent on machine performance; local commit.

## Definition of done

The server runs from the existing binary, the MCP client discovers and executes the defined tools, and the transport does not weaken the Core rules. Evidence includes a real stdio process, target control, redaction, the schema/result budget, cancellation and a publish smoke. Documentation changes without implementation do not meet this criterion.
